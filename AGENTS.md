# Smart Travel Itinerary Generator for Malaysian Cultural Tourism

Notes for AI coding agents (Claude Code, Codex and others). `CLAUDE.md` imports this file, so
edit the notes here only.

## What this is

A web application that builds day-by-day travel itineraries for cultural tourism in Malaysia. A
traveller enters preferences (budget, transport mode, interests, states and districts, party
size). The system then picks cultural places, hotels and food, puts the stops in a good order,
shows the routes on a map and exports the plan as a PDF. An admin side manages the cultural
knowledge base, place imports, pending suggestions, users and reports. It began as a final-year
project and is now kept as a clean, working, self-hosted system.

## How it is built

- PHP 8.2 and MariaDB 10.4 under XAMPP on Windows. Plain PHP pages, no framework. Composer brings
  only dompdf (PDF export) and PHPMailer (mail).
- Pages: `index.php`, `role_select.php` (traveller or admin), `auth/`, `preference/`,
  `itinerary/` (generate, review, view, share, `export_pdf.php`), `cultural/` (guide, reviews,
  place suggestions), `traveller/`, `admin/`.
- `api/`: the endpoints the pages call for address search, routes, weather, live buses, road
  conditions and the AI assistants.
- `services/`: the logic (planner, routing, place sync, open-data clients, AI). `config/`:
  `env_loader.php`, `db_connect.php`, `security.php` (CSRF helpers).
- `tools/`: `sync_places.php` (place sync), `sync_places_weekly.bat` (the weekly run),
  `migrate.php` (applies `database/migrations/`, records them in `schema_migrations`),
  `check_planner.php` and `export_schema.php`. `database/schema.sql` and
  `database/seed_reference.sql` are the clean install; `travel_itinerary_db.sql` is a full dump
  with sample accounts. `storage/cache/`, `storage/logs/` and `uploads/` are not in git.
- Itineraries are generated by rules, not by an AI model: `itinerary/generate_itinerary.php` calls
  `ItineraryGenerator`, which uses `PlannerRules` (every rule, once), `PlannerCandidates`,
  `ItineraryDayBuilder` and `ItineraryRouteOptimiser` and stores the trip in one transaction.
  Hard rules and soft preferences are separate; meals and weather are part of the plan.
  `services/ItineraryEditService.php` is the one place that changes a stored itinerary (the
  page controls, `api/itinerary_edit.php`, the review pages and the AI editor all call it).
  `docs/PLANNER.md` has the rules and numbers.
- The traveller pages are in English, Malay and Chinese: `config/i18n.php` and `lang/`. Add every
  new text to all three files. The PDF is English or Malay.
- The AI features (travel assistant and chat, accessibility needs, admin report analysis) use a
  local Ollama model through `services/OllamaClient.php`. There is no hosted AI service.
- Maps, places, photos, routes, weather and live transport use open data only. The table in
  `docs/OPEN_DATA.md` lists every source, its licence and the credit that must stay on the page.

## Rules

1. **Databases.** The real database is `travel_itinerary_db` (the `DB_NAME` in `.env`). Test only
   on the copy `travel_itinerary_db_ctest`. Never write test data to the real one, and change the
   real one only after the owner agrees to that change. To use the test copy without touching
   `.env`, set the variable for the command: `DB_NAME=travel_itinerary_db_ctest php ...` in Git
   Bash, or `$env:DB_NAME = 'travel_itinerary_db_ctest'` first in PowerShell.
   `config/env_loader.php` keeps a variable that is already set.
2. **Git.** Work on the branch `consolidate/single-source` and leave `main` alone. Commits stay
   local. Never push unless the owner says so in that conversation.
3. **Cost.** Free, open-source and self-hosted only. No Google Maps, Places or other Google Cloud
   service, and no other paid or card-required API. The one exception is the optional TomTom
   traffic key.
4. **Secrets.** `.env` holds passwords and keys. Never print, copy or commit its values; name the
   keys only (`.env.example` lists them).
5. **Place sync.** `php tools/sync_places.php --all --no-publish` stages new places for review.
   Without `--no-publish` it also publishes the places that score high enough
   (`PLACE_SYNC_AUTO_PUBLISH_MIN`), on whichever database it runs against, so keep the flag unless
   the owner asks otherwise. `--dry-run` saves nothing.
6. **Credits.** Keep the source credits on pages and in the PDF when you change them. They are
   licence conditions.
7. **Language.** Reply to the owner in Simplified Chinese. Write code, comments, commit messages
   and documents in English.

## Run and check

- The site on the real database, with XAMPP's Apache and MariaDB running (`StartFYP.bat` starts
  them):
  `http://localhost/Development-Of-a-Smart-Travel-Itinerary-Generator-For-Malaysian-Cultural-Tourism/`
- PHP is `C:\xampp\php\php.exe`; the MariaDB client is `C:\xampp\mysql\bin\mysql.exe`.
- After editing a PHP file, run `C:\xampp\php\php.exe -l <file>`. There is no unit test suite.
  After a planner change run `DB_NAME=travel_itinerary_db_ctest php tools/check_planner.php`
  (`--scenario=<name>` for one; it refuses a database not ending in `_ctest` and stays offline
  unless `--road` is given).
- A schema change is a dated file in `database/migrations/` that is safe to run twice. Apply it
  with `php tools/migrate.php` (`--status` lists; a database not ending in `_ctest` needs
  `--confirm=<name>`), then refresh the clean install with `php tools/export_schema.php` on the
  test copy.
- A site on the test copy: the `test-copy` configuration in `.claude/launch.json` starts PHP's
  built-in server on `127.0.0.1:8765` with the test database. Open `http://preview.localhost:8765/`
  (traveller) or `http://admin.localhost:8765/` (admin); these host names keep its cookies apart
  from the real site. `.claude/` exists only on the owner's machine and is not in git.
